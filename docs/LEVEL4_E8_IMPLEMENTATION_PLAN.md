# E8 plan (write-up only — not started)

**Naming note:** no pre-existing, unrelated `docs/E8_IMPLEMENTATION_PLAN.md` stub exists (unlike E5/E6/E7's own disambiguation notes) — this filename is free. Nothing below is implemented. No code in this pass adds validation harnesses, visualization, canonicalization tooling, or freezes any public surface.

## Where E7 leaves off

Level 4 now has a complete, additive chain — `MotionHint` (E1) → `TemporalHistory`/`TemporalRecord` (E2) → `TemporalConsistency` (E3) → `TemporalStabilization` (E4) → rotation compensation (E5) → `MotionAwareReliability` (E6) → `TemporalPersistence` (E7) — each phase built, tested, and documented in isolation against synthetic fixtures and a real (but static) calibration file. What has **not** happened at any point across E1-E7:

- **A single end-to-end run exercising all seven phases together, over a realistic multi-frame sequence with genuine motion, has never been executed or captured.** Every phase's own test suite constructs its own minimal pipeline configuration (typically enabling only that phase plus its direct prerequisites) and typically feeds either a single static synthetic stereo pair processed repeatedly, or small synthetic depth-snapshot arrays directly into a `temporal.*` function/tracker. No test in this repository today builds one `DepthPerceptionPipeline` with `enable_temporal`, `enable_temporal_stabilization`, `enable_rotation_compensation`, `enable_motion_aware_reliability`, and `enable_temporal_persistence` **all simultaneously `True`**, feeds it a longer (10+ frame) sequence of *varying* synthetic or real imagery with accompanying `MotionHint` samples, and inspects the full resulting chain frame-by-frame.
- **No visual proof exists for E3-E7 at all.** Level 3's own `docs/VALIDATION_REPORT.md`/README carry a real snapshot + GIF (`docs/assets`) demonstrating single-frame geometry on real hardware. Nothing analogous exists for temporal consistency, stabilization, rotation compensation, reliability, or persistence — every claim about their behavior today is backed by numeric test assertions only (agreement fractions, state strings, per-cell counts), never a rendered depth/persistence-state visualization a human can look at and sanity-check.
- **No real-hardware capture has been run through any Level 4 phase.** `docs/VALIDATION_REPORT.md`'s only real-camera capture predates Level 4 entirely (2026-08-05, Level 0-2 only, later extended to Level 3 E7's own real-scene recapture — see `docs/IMPLEMENTATION_STATUS.md`'s README-asset-recapture entries). Every E2-E7 number in this repository is synthetic-fixture-derived.
- **The Level 4 public surface has never been canonicalized/frozen.** `docs/LEVEL4_PUBLIC_API.md`/`docs/LEVEL4_CONTRACTS.md`/`docs/LEVEL4_ARCHITECTURE.md` were updated at E1-E2 and then only lightly touched at E7 (this pass) — E3-E6 each recorded their own API impact in their own standalone `*_IMPLEMENTATION_PLAN.md` document rather than in the three canonical Level 4 reference documents. There is no single, current, complete Tier 1/2/3 accounting of the entire Level 4 surface (`PipelineConfig`'s 13 new fields across E2-E7, `DepthPerceptionResult`'s 6 new fields, every new `temporal.*` Tier 3 symbol) in one place — a reader has to assemble it from seven separate per-phase documents plus `tests/test_public_api.py`'s own `INTERNAL_SYMBOLS` list.

## What E8 should do — three genuinely different pieces of work, not mutually exclusive

### Piece A: full-chain integrated validation (software only, no new hardware)

1. A new, explicit integration test (or small suite) that constructs one `DepthPerceptionPipeline` with **every** Level 4 flag enabled simultaneously, runs it over a longer synthetic sequence deliberately designed to exercise every E7 state at least once in the same run (a stationary synthetic obstacle patch that: appears fresh → repeats until `PERSISTENT` → is briefly occluded (dropout grace) → reappears → is then genuinely removed (repeated absence → `DISAPPEARING` → expiration) → while a *second*, independently-moving patch appears fresh partway through and must read `NEW` immediately without being suppressed by the first patch's own history), combined with a `MotionHint` sequence that includes at least one genuine rotation large enough to exercise E5/E6's own angular-motion thresholds, and at least one deliberately `UNRELIABLE` frame (e.g. an injected large/contradictory jump) to exercise E7's own Rule 7 gate under real pipeline wiring, not just the direct-tracker unit tests E7 itself added.
2. Assert the full cross-phase causal chain holds together in one real run: E3's `CONTRADICTORY` frame → E6 downgrades to `UNRELIABLE` → E7 correctly freezes (does not reinforce) that frame — this three-hop chain is exercised piecemeal today (E6's own tests prove step 2, E7's own tests prove step 3 by directly passing `UNRELIABLE` into the tracker) but never as one continuous, pipeline-driven causal proof.
3. Re-run the full test suite's own timing (`processing_time_ms` breakdown, already logged per-stage at `DEBUG`) with all seven phases enabled together, to characterize real combined overhead (each phase's own `docs/*_IMPLEMENTATION_PLAN.md` characterizes its own marginal cost in isolation; the combined cost with every flag on has never been measured).

### Piece B: visual proof

A rendering/capture pass (could reuse this repository's existing README asset-capture scripts, `docs/assets`, and countdown-capture tooling already built for Level 3) producing at minimum: one still image or short GIF showing `TemporalPersistence.state_grid` overlaid on (or alongside) the corresponding `depth_map`/RGB frame, color-coded by `NEW`/`PERSISTENT`/`DISAPPEARING`/`NO_EVIDENCE`, across a short real or synthetic sequence — something a human reviewer can look at and confirm "yes, that obstacle really did stay classified `PERSISTENT` while sitting still, and the empty region really did stay `NO_EVIDENCE` throughout" without reading test assertions. Real-hardware capture (Piece C) would make this far more convincing than another synthetic fixture, but a synthetic visualization is still strictly better evidence than the current all-numeric test suite alone.

### Piece C: real-hardware / real-motion capture

Requires physical access to a stereo rig capable of being deliberately panned/rotated (to produce genuine `MotionHint`-worthy angular motion, ideally from a real or simulated-but-timestamp-realistic IMU — see `docs/LEVEL4_SIMULATED_IMU.md`, still not built) and a scene with at least one genuinely static object and one object that is physically removed partway through the capture (to produce a real `DISAPPEARING`/expiration event, not a synthetically-zeroed depth array). This is the most expensive piece (hardware access, capture time, potentially a `MotionHint` producer that does not exist yet) and the one most likely to surface a real bug no synthetic fixture would — same reasoning `docs/E7_IMPLEMENTATION_PLAN.md`'s own Direction B gave for Level 3.

### Piece D: canonicalization / freeze

Once A (and ideally B) are complete: rewrite `docs/LEVEL4_ARCHITECTURE.md`, `docs/LEVEL4_CONTRACTS.md`, and `docs/LEVEL4_PUBLIC_API.md` as complete, current, single-source-of-truth documents covering E1-E7 together (not the current "E1-E2 fully, E7 lightly patched, E3-E6 pointer-only" state), mirroring the discipline `docs/LEVEL3_ARCHITECTURE.md`/`docs/LEVEL3_CONTRACTS.md`/`docs/LEVEL3_PUBLIC_API.md` already apply to the frozen Level 3 surface. Add an explicit "Level 4 frozen as of E8" marker (mirroring `docs/IMPLEMENTATION_STATUS.md`'s existing 2026-08-07 Level 3 E7 freeze note) once this is done, so a future phase inherits the same audited-baseline discipline this document's own "pre-change state" sections have followed since Level 4 E1.

## This plan takes no position on which piece(s) a future E8 pass should actually do

A, B, C, and D have different costs and different owners (C needs physical hardware access; A and D are pure software; B is pure software but benefits enormously from C). Resolving which combination "E8" actually means is the first concrete decision a future pass needs to make — not assumed here, matching `docs/E7_IMPLEMENTATION_PLAN.md`'s own precedent for not choosing between its own Direction A/B at Level 3.

## Explicitly not part of this plan either

Any new perception capability (occupancy/voxel mapping, vehicle envelope, collision-risk scoring — all still open, restated at every phase since Level 3 E4), semantic perception, learned/neural models, additional IMU capability beyond what `MotionHint` already carries, planning, localization — all remain out of scope, matching every prior phase's non-goals. E8 is validation, visualization, and documentation freeze — not a new algorithm phase.

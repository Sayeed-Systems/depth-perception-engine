## What "pending" means, precisely

Not "untested" — E1-E7 each have dedicated unit/integration test suites (698 tests through E7, 715 through E8's own software-only integration pass, all passing — see the E8 final report), and E8's own Part A ran the complete seven-stage chain together over realistic multi-frame synthetic sequences. Real stereo geometry has now been exercised too (below). What is still missing is specifically **real IMU/motion data**: real gyroscope readings with real hardware timestamp jitter, and a real agent/camera that actually rotates by a known amount while being observed. No claim in this repository about Level 4's behavior under those two specific conditions has been verified — only claims about its behavior on synthetic stand-ins for them.

## What would unblock each item

Physical access to: a real stereo rig (global-shutter, same class as Level 3's own hardware validation used), a real IMU or flight-controller gyroscope stream time-synchronized to that rig, a real or reference-instrumented rotation stage/turntable (or a hand-rotated rig with an independent ground-truth angle source) for the rotation-specific items, a measured camera-to-body/IMU extrinsic (checkerboard or equivalent calibration procedure against the real mounting), and a Jetson Orin Nano (or the actual target board) to run the identical E8 integration scenarios on. None of this is software work — `depth_perception_engine` itself needs no code change to accept real inputs; every Level 4 contract (`MotionHint`, `StereoObservation`, `PipelineConfig`) already accepts real sensor data in exactly the same shape as the synthetic fixtures used throughout E1-E8.

## Why this is not fabricated here

This phase's own instructions were explicit: "DO NOT fabricate this." No synthetic result in this repository is described anywhere as a hardware measurement, and no number in this document, `docs/LEVEL4_E8_INTEGRATION_REPORT.md`, or `docs/VALIDATION_REPORT.md`'s Level 4 addendum is presented as having come from real IMU data or a Jetson board. The one row marked done above genuinely was captured on real hardware — the console log, frame count, and per-frame reliability/persistence values in `docs/VALIDATION_REPORT.md` are the real output of that real run, not illustrative numbers — and the simulated `MotionHint` used alongside it is badged as simulated in the artifact itself, not silently presented as more than it is. Software Level 4 remains frozen with this checklist attached, four rows still explicitly incomplete, rather than with a fabricated "fully validated on hardware" claim.

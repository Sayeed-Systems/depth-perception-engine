# DPE V1 provider contract — Phase D1 (design record) + Phase D2/D3/D4/D5/D6/D7/D8 (implemented)

**Status: D1 design APPROVED; D2 through D8 IMPLEMENTED.** `GeometryFrame` exists in code today, including the neutral `RegionEvidence`/`ClearanceEvidence` evidence D3 added, the `SurfaceEvidence` local-surface-geometry evidence D4 added, the `BoundaryEvidence` geometric-discontinuity evidence D5 added, the `OpeningEvidence` geometric-opening evidence D6 added, the coverage/bearing refinement D7 made to `ClearanceEvidence`, and the `GeometryFrameQuality` structured quality/uncertainty contract D8 added — see "D2 implementation record" through "D8 implementation record" at the end of this document for exactly what was built, where each diverged from the prior phase's own open items, and the contract issues discovered along the way (D2 flagged one; D3 resolved it). The rest of this document is preserved as written at D1 time (a design record, not a living spec) — read the D2-D8 sections for current, as-built ground truth.

Builds on `docs/PUBLIC_API.md` (current Tier 1/2/3 accounting), `docs/LEVEL4_CANONICAL_REFERENCE.md` (current, authoritative Level 4 description), and the D0 reconnaissance findings — this document does not repeat what those already establish correctly; it resolves the specific D0 open questions the architect decided on for D1.

## Architect decisions this contract implements (verbatim scope)

1. `NavigationDecision`/behavioral commands are **not** part of the authoritative V1 contract. Existing behavior is preserved for compatibility.
2. V1 exposes neutral geometric/spatial evidence only — no navigation behavior encoded into the new representation.
3. Threat/obstacle code's *geometric* evidence (distance, occupancy, validity) may remain in DPE; its *behavioral* threshold/policy output must not define the V1 contract.
4. Level 4 temporal work stays DPE-owned and should eventually attach to the provider API without exposing unnecessary internals.
5. DPE owns geometry-only future capabilities (surfaces, normals, boundaries, openings, clearance) — not designed in this pass.
6. `mp01_perception` must not break; existing outputs remain compatibility APIs until the new contract is stable.

## 1. Proposed authoritative DPE V1 output structure

**Decision: introduce a new, purpose-built type, `GeometryFrame` — attached to the existing `DepthPerceptionResult` as one additive field, not a replacement.**

`GeometryFrame` is *not* a new top-level return type from a new processing object. `DepthPerceptionPipeline` remains the one canonical entry point (unchanged naming policy, `docs/PUBLIC_API.md`); `DepthPerceptionResult` remains the one output shape. `GeometryFrame` is a new, additive, `Optional`, default-`None` field on it:

```python
DepthPerceptionResult.geometry_frame: Optional[GeometryFrame] = None
```

populated only when a new opt-in flag, `PipelineConfig.enable_geometry_frame: bool = False`, is `True` — identical "opt-in, zero cost when disabled, existing callers unaffected" discipline every prior Level 3/4 phase already used (`enable_geometry`, `enable_temporal`, …).

**Why an additive field, not a replacement type, and not a second processing object** (resolves the D0 question "should `DepthPerceptionResult` evolve or is a new `GeometryFrame`-style type cleaner" — the answer is both, combined):

- Satisfies decision 6 structurally, not by promise: zero existing field is touched, so `mp01_perception`'s current `result.traversability_mask`/`result.obstacles` access is provably unaffected — the same guarantee `tests/test_level4_integration_e8.py::TestRawLevel3EvidenceUnchanged`-style tests already prove for every prior additive field.
- Matches "prefer adapting existing types/code over rewriting working systems" literally: every single Level 3/4 capability added since this repository's baseline (`geometry`, `geometry_body`, `obstacle_cloud`, `free_space_rays`, `geometry_metrics`, `temporal_admission_status`, `temporal_consistency`, `temporal_stabilization`, `rotation_compensation_status`, `motion_aware_reliability`, `temporal_persistence`) used exactly this pattern. `GeometryFrame` is the same pattern, once, for the whole neutral-evidence contract, rather than N more individual top-level fields.
- A second top-level return type (or a second processing object) would resurrect exactly the `DepthPerceptionEngine`-vs-`DepthPerceptionPipeline` naming-duplication problem `docs/PUBLIC_API.md` already explicitly rejected once.

## 3. Compatibility API boundary

Precise line, stated once so nothing downstream has to guess:

- **Authoritative V1 contract** = `DepthPerceptionResult.geometry_frame` (once D2 implements it) — pure geometric/spatial/temporal evidence, zero behavioral judgment, zero vehicle-specific threshold.
- **Compatibility/legacy** = every other current `DepthPerceptionResult` field, unchanged, indefinitely available, never removed by this migration. Specifically: `traversability_mask` (and everything it embeds — `RegionStats`, `RegionClass`, `NavigationDecision`), `obstacles` (and `BeamReading.status`), `confidence` in its current definition.
- **The geometric evidence embedded inside the compatibility layer is real and not wasted** (decision 3): `RegionStats`' own signals (`valid_pct`, `depth_avg_m`/`depth_median_m`/`depth_min_m`/`depth_max_m`, `texture_score`, `entropy`, `gradient_magnitude`) and `ThreatAssessor`'s per-beam `distance_m` are legitimate evidence sitting *inside* behavior-shaped containers (`RegionClass`, CLEAR/CAUTION/BLOCKED). Extracting them into neutral types is real, identified, **future** work (§5/§6) — not done in D1, and not blocking `GeometryFrame`'s first useful version, because the geometry pipeline (`geometry`/`obstacle_cloud`/`free_space_rays`/`geometry_metrics`) is *already* a complete, neutral occupied/free/unknown provider independent of `RegionAnalyzer`/`ThreatAssessor` entirely.
- No existing symbol is renamed, moved, or deprecated-with-a-warning in D1. "Compatibility" here means "not promoted into the new contract," not "scheduled for removal" — no removal timeline is set by this document; that is a future decision, not implied by this one.

## 4. Temporal integration

Resolves decision 4 ("attach without exposing unnecessary internals"):

- `GeometryFrame` carries the same five already-computed per-frame Level 4 result objects `DepthPerceptionResult` already exposes — `temporal_consistency`, `temporal_stabilization`, `rotation_compensation_status`, `motion_aware_reliability`, `temporal_persistence` — as direct references (same object each frame, no copy, no recomputation, no new algorithm).
- `GeometryFrame` does **not** expose `temporal.TemporalHistory` (the bounded buffer object) or `temporal.TemporalRecord` (its internal chronology entries) — those remain exactly what they are today: `DepthPerceptionPipeline`-internal bookkeeping, reachable only via the existing `.temporal_history` property for a caller that specifically wants to inspect chronology, never part of the per-frame evidence contract. This is the literal "without exposing unnecessary internals" boundary.
- `temporal_admission_status` is **not** carried onto `GeometryFrame` — it is chronology bookkeeping metadata (E2's own frozen framing: "pure metadata about this frame's own chronology-admission outcome... never a reinterpretation of evidence"), not evidence itself. It remains readable from `DepthPerceptionResult` directly.
- **Tier gap this creates, flagged for D2, not resolved here**: `GeometryFrame` is intended as a Tier 1 type, but four of the five temporal fields it carries (`TemporalConsistency`, `TemporalStabilization`, `MotionAwareReliability`, `TemporalPersistence`) are currently Tier 3 (`docs/PUBLIC_API.md`). A Tier 1 type structurally containing Tier 3-typed fields is an inconsistent public contract — a caller cannot type-hint `GeometryFrame.temporal_persistence: Optional[TemporalPersistence]` without an internal-path import. D2 should promote these four types (plus `MotionHint`, symmetrically) to Tier 1, mirroring the exact precedent `docs/PUBLIC_API.md` already used for `RegionClass`/`NavigationDecision`/`TextureClass`/`RegionStats`. This is pure API-surface promotion — zero behavior change, zero risk to `mp01_perception` (Tier 3 paths keep working; nothing is removed).

## 5. Types that must be added/changed in later phases (explicitly NOT designed in D1)

Per decision 5 and the task's own "Do NOT yet implement surfaces/openings/new algorithms" — named, not designed:

- **`GeometryFrame` itself** — the dataclass this document specifies does not exist in code yet. D2's job.
- **Tier 1 promotion** of `TemporalConsistency`, `TemporalStabilization`, `MotionAwareReliability`, `TemporalPersistence`, `MotionHint` (and their state-constant classes) — mechanical, low-risk, recommended for D2.
- **`ClearanceEvidence`** (working name only) — a neutral extraction from `ThreatAssessor`'s per-beam `distance_m`, decoupled from its CLEAR/CAUTION/BLOCKED status labels and from `caution_distance_m`/`clear_distance_m`-style vehicle thresholds. Requires a real refactor of `ThreatAssessor`/`obstacles/threat_assessment.py` — explicitly out of scope for D1 ("avoid implementation refactors"), and its exact shape (per-beam? per-sector angle? does it reuse `n_beams`?) is an open design question, not decided here.
- **`RegionEvidence`** (working name only) — a neutral extraction of `RegionAnalyzer`'s per-region signals (`valid_pct`, depth stats, `texture_score`, `entropy`, `gradient_magnitude`), decoupled from `RegionClass`'s occupancy/behavior labels. Same "real refactor, not designed here" status.
- **Surface normals / local orientation** — no existing producer anywhere in this repository (confirmed in D0); a genuinely new capability, needs its own design pass.
- **Boundary/discontinuity evidence** — same status; `RegionAnalyzer.gradient_magnitude` is an image-intensity signal, not a depth-discontinuity one, and is not a starting point without independent evaluation.
- **Opening/gap evidence** — same status; no existing partial implementation to build from at all.
- **Unified geometric confidence/health** — `geometry_metrics.valid_fraction`/`classify_geometry_quality()` is the leading candidate (already neutral, already exists, already tested) but formally adopting it as `GeometryFrame`'s confidence signal, and deciding whether/how it folds in `motion_aware_reliability.state`, is a real decision left open.
- **`pipeline.api` (Tier 2) Level 4/`GeometryFrame` support** — the stateless one-shot functions currently have no temporal wiring at all (D0 finding); whether they gain it is undecided.

## D2 implementation record

**CRITICAL ARCHITECTURAL INVARIANT (restated from the D2 task, now enforced in code):** `GeometryFrame` is the FINAL authoritative DPE V1 perception-data contract for any larger external perception system. A future `hybrid_perception_engine` (or any other consumer) must consume DPE geometric evidence ONLY through `GeometryFrame` — never by importing DPE algorithm internals, `TemporalHistory`/`TemporalRecord`, `RegionAnalyzer`, `ThreatAssessor`, traversability internals, `NavigationDecision`, intermediate pipeline state, or legacy `DepthPerceptionResult` fields beyond `geometry_frame` itself. `DepthPerceptionResult.geometry_frame` is ONLY a migration/backward-compatibility mechanism.

**Location, resolving the first open item above:** `src/depth_perception_engine/geometry/provider.py` — a new, dedicated module inside the existing `geometry/` subpackage, deliberately not `models/result.py` (the D2 task's own instruction: "prefer a dedicated geometry/provider-facing module") and deliberately not `geometry/types.py` (that module frames itself as Level 3 interfaces only; `GeometryFrame` spans Level 3 geometry *and* Level 4 temporal evidence). `GeometryFrame` imports only from `geometry.types` and `temporal.types` — zero dependency on `models.result`, so no circular import is created despite `DepthPerceptionResult` itself carrying a `geometry_frame: Optional[GeometryFrame]` field. Construction (`fusion.result_builder.build_geometry_frame(result)`) lives in `fusion/result_builder.py` instead, reading every field directly off an already-built `DepthPerceptionResult` — zero recomputation, by construction.

**`frame_id`, resolving the second open item above:** `GeometryFrame.frame_id` is always `frames.FrameId.CAMERA_OPTICAL_LEFT` — `disparity_map`/`depth_map`/`geometry` are always camera-optical-frame in this pipeline. `geometry_body`/`obstacle_cloud`/`free_space_rays` each declare their own differing `frame_id` (`BODY`) on themselves, exactly the "nested object explicitly declares a different frame" exception the D2 task specified — no duplication, no second frame concept invented.

**Tier 1 promotion actually performed:** `TemporalConsistency`, `TemporalConsistencyState`, `TemporalStabilization`, `TemporalStabilizationState`, `RotationCompensationStatus`, `MotionAwareReliability`, `MotionAwareReliabilityState`, `TemporalPersistence`, `TemporalPersistenceState`, `TemporalPersistenceCellState` — the four RESULT dataclasses `GeometryFrame` carries, plus each one's own state-constant class (needed to meaningfully interpret `.state`/`.state_grid` without an internal import — the same "promote the enum alongside the dataclass" precedent `RegionClass` already set). `MotionHint` was **not** promoted (§4's "symmetrically" suggestion was not followed): it is not one of `GeometryFrame`'s own fields, and the D2 task's authorization was specifically "the mature Level-4 RESULT/EVIDENCE types **required by `GeometryFrame`**" — `MotionHint` is a pipeline *input* type, not part of this output contract. `TemporalHistory`, `TemporalRecord`, `TemporalAdmissionStatus`, `TemporalPersistenceTracker`, and every `compute_*` algorithm function remain Tier 3, per the D2 task's explicit "Do NOT expose" list.

**Contract issue discovered, deliberately left unresolved (D2 boundary, not a D2 bug):** `GeometryFrame` is Tier 1, but four of its own fields (`geometry`, `geometry_body`: `geometry.PointCloud`; `obstacle_cloud`: `geometry.ObstacleCloud`; `free_space_rays`: `geometry.FreeSpaceRays`; `geometry_metrics`: `geometry.GeometryMetrics`) are typed against classes that remain Tier 3 (`docs/PUBLIC_API.md`, `docs/LEVEL3_PUBLIC_API.md`'s own explicit "PointCloud deliberately not promoted even once it had a real producer" decision). A caller can read `geometry_frame.geometry.points` freely (attribute access needs no import), but cannot write `def handler(pc: PointCloud)` or `isinstance(x, PointCloud)` without an internal `depth_perception_engine.geometry.types` import. The D2 task's own promotion authorization was scoped specifically to "the mature **Level-4** RESULT/EVIDENCE types required by `GeometryFrame`" — `PointCloud`/`ObstacleCloud`/`FreeSpaceRays`/`GeometryMetrics` are Level 3, not Level 4, so promoting them was outside D2's authorized scope even though the same structural argument §4 already made for the Level 4 types applies to them identically. **Flagged as an open D3 decision**, not resolved here.

**Tests:** `tests/test_geometry_frame.py` (new, 18 tests covering all 10 scenarios the D2 task named) plus one existing frozen-contract test updated (`tests/test_pipeline_geometry.py::TestResultContract::test_existing_fields_unchanged_in_name_type_and_order`, extended to expect `geometry_frame` appended as the new last field) and `tests/test_public_api.py` (TIER_1_SYMBOLS/DUPLICATED_PATHS/INTERNAL_SYMBOLS updated for the 11 newly-public symbols). ## D4 implementation record

**The first genuinely new geometric algorithm.** Unlike D2 (pure assembly) and D3 (pure extraction), D4 adds a real computation: deterministic, bounded local-plane (surface normal) estimation over an existing organized `PointCloud`. Answers "what surface geometry is observable here?" — never "can a vehicle traverse/land/navigate here?" No `RegionClass`/`NavigationDecision`/`ThreatAssessor` import anywhere in `geometry/surface.py`; no field, state, or label named "road"/"ground"/"wall"/"landing surface"/"traversable" exists anywhere in the new type.

**`SurfaceEvidence`** (`geometry/surface.py`, new module — co-located with its algorithm, matching `geometry_metrics.py`'s own "type + producer together" precedent for post-E1 additions, unlike D3's pure-extraction types which live in `provider.py`): `frame_id` (copied from the source cloud — generic, not hardcoded to BODY), `row`/`col`/`x1`/`y1`/`x2`/`y2` (spatial identity/extent, mirrors `RegionEvidence`), `support_count`/`support_fraction` (coverage — always populated, 0/0.0 is a legitimate value), `centroid_m`/`normal`/`planarity` (all three `Optional`, `None` together whenever a cell has insufficient or degenerate support — centroid alone can never be populated without the other two, since a mean position without a well-defined plane would be a partial-fabrication risk the D4 task explicitly rules out).

**Algorithm:** the source cloud's pixel grid is partitioned into `surface_grid_rows x surface_grid_cols` cells (same `np.linspace` boundary convention `traversability.SceneInterpreter` already uses for its own region grid, reimplemented independently — `geometry/surface.py` imports nothing from `traversability`). For each cell with `>= surface_min_support_count` valid points: compute the 3x3 covariance matrix of the cell's points, eigendecompose it (`np.linalg.eigh`, ascending eigenvalue order for a real symmetric input), take the smallest-eigenvalue eigenvector as the normal, and compute `planarity = clip(1 - 3*lambda_min/sum(lambda), 0, 1)` (1.0 = points lie exactly on a plane, trending toward 0.0 as the neighborhood becomes isotropic/non-planar — the classical PCA "surface variation" measure, inverted so higher means better fit). A degenerate cell (near-zero total variance — every point coincides) reports `normal=None`/`planarity=None` but keeps a valid `centroid_m` (the mean is always well-defined).

**Coordinate frame:** every `SurfaceEvidence.frame_id` is copied directly from the input `cloud.frame_id` — the function has no built-in BODY/CAMERA_OPTICAL_LEFT opinion (matches `build_obstacle_cloud`'s own genericity). In this pipeline's actual wiring, the input is always `geometry_body` (BODY frame), so `centroid_m`/`normal` are always BODY-frame in practice.

**Normalization convention:** `normal`, when not `None`, is always a unit vector (`np.linalg.norm(normal) == 1.0` up to floating-point precision) — enforced by explicit division, not merely assumed from `eigh`'s own near-unit output. Proven with an exact analytic tilted-plane construction (`tests/test_surface_geometry.py::TestNormalization`), not just "a value exists."

**Orientation/sign convention:** an eigenvector's sign is mathematically ambiguous (`n` and `-n` solve the same eigenproblem). Resolved deterministically by orienting `normal` toward `viewpoint` (in practice, `body_T_camera_left.translation` — the same origin already used by `build_obstacle_cloud`/`build_free_space_rays`): flip iff `normal . (viewpoint - centroid) < 0`. This is the standard, purely geometric "orient toward the sensor" convention from point-cloud processing (e.g. PCL) — it encodes where the sensor observed the surface FROM, nothing about "up," "outward," or any surface-type judgment. Proven with an exact analytic flat-plane construction where the expected sign is hand-derivable (`tests/test_surface_geometry.py::TestKnownPlaneProducesExpectedNormal::test_flat_plane_normal_is_exact`, expecting exactly `(0, 0, -1)`) and a viewpoint-flip determinism test.

**Invalid/insufficient-support behavior:** a cell below `surface_min_support_count` gets `centroid_m=None, normal=None, planarity=None` — explicitly unknown, never fabricated/interpolated — while `support_count`/`support_fraction` remain populated (real, informative values, not "no data"). Proven directly: an all-invalid synthetic cloud produces zero planes across every cell (`tests/test_surface_geometry.py::TestInvalidDepthDoesNotFabricateSurfaces`), and a cloud with exactly `min_support_count - 1` points reports `None` while still reporting the real count (`TestInsufficientSupportRepresentedExplicitly`).

**`GeometryFrame` addition:** `surface_evidence: Optional[List[SurfaceEvidence]]`, appended as the new last field. Unlike `region_evidence`/`clearance_evidence` (D3, pure extractions with no `DepthPerceptionResult` twin), `surface_evidence` gets a real `DepthPerceptionResult.surface_evidence` field too — because it is genuinely NEW computed evidence, not a re-labeling of already-existing data, the same "new capability gets a real result field" pattern every Level 3/4 phase before D3 used. `build_geometry_frame()` reads `result.surface_evidence` directly (object identity, zero recomputation — proven in `TestGeometryFrameExposesSurfaceEvidence::test_zero_recomputation_same_object_as_result`), preserving its own "pure reader" invariant unchanged since D2.

**Config:** `enable_surface_geometry: bool = False` (nested under `enable_geometry`, same dependency `enable_obstacle_geometry`/`enable_free_space_rays` already have on a `geometry_body` cloud existing), `surface_grid_rows: int = 3`, `surface_grid_cols: int = 3` (validated `>= 1`, matching `traversability_grid_rows/cols`), `surface_min_support_count: int = 30` (validated `>= 3` — the geometric minimum to determine a plane). All default-preserving; no existing flag's behavior changed.

**Performance (measured, not estimated):** on this development container's own CPU (not Jetson — explicitly flagged, same discipline as `docs/VALIDATION_REPORT.md`'s own Level 4 benchmark), 320x240 synthetic stereo, 20-frame average: geometry+obstacle+free-space-rays alone is 23.79 ms/frame; adding `enable_surface_geometry` (3x3 grid) is 26.26 ms/frame — **+2.47 ms/frame (~10%)**. Bounded by `surface_grid_rows * surface_grid_cols` (a small configured constant, 9 cells by default), not by image resolution — a 3x3 eigendecomposition per cell is O(1) work; the per-cell point-extraction pass is the dominant cost, still small relative to the SGBM disparity stage it runs downstream of.

**Tests:** `tests/test_surface_geometry.py` (new, 23 tests) covering all 12 D4 scenarios — analytically constructed flat and tilted planes with hand-derivable expected normals (not merely "a value exists"), normalization, sign-convention determinism and viewpoint-flip behavior, all-invalid and below-threshold non-fabrication, mixed valid/invalid grids, frame-contract checks, full-pipeline `GeometryFrame` exposure with object-identity zero-recomputation proof, the disabled-flag path, legacy-output byte-identity, and no-behavioral-leakage (field-name and import-surface checks, mirroring D3's `TestD3NoBehavioralLeakage`). Plus 3 existing frozen-contract tests updated (`tests/test_geometry_frame.py`'s field-list test, `tests/test_pipeline_geometry.py::TestResultContract`'s field-order test, `tests/test_public_api.py`'s `TIER_1_SYMBOLS`/`DUPLICATED_PATHS`/`INTERNAL_SYMBOLS`). Full suite: **776 passed, 0 failed**.

## D5 implementation record

**Goal, restated:** identify where observed physical geometry changes significantly or terminates — geometric evidence only, never a semantic edge class, never a navigation decision, never an inferred opening.

**`BoundaryEvidence`** (`geometry/boundary.py`, new module — co-located with its algorithm, same "type + producer together" convention D4's `SurfaceEvidence` established for post-D1 additions): `frame_id` (generic, copied from the caller), `row`/`col`/`direction` (which cell, and which neighbor — `BoundaryDirection.RIGHT`/`DOWN`), `x1`/`y1`/`x2`/`y2` (pixel-space bounding box spanning BOTH adjacent cells — the boundary's own spatial extent), `support_fraction_from`/`support_fraction_to` (validity/support for each side), `state` (`BoundaryState.OBSERVED_DISCONTINUITY`/`NO_DISCONTINUITY`/`INSUFFICIENT_EVIDENCE`), `depth_step_m`/`orientation_change_rad` (both `Optional`, `None` together whenever `state == INSUFFICIENT_EVIDENCE`).

**Algorithm:** depth_map is partitioned into its OWN independent `boundary_grid_rows x boundary_grid_cols` grid (same `np.linspace` convention D4 already reimplemented independently — no dependency on `traversability.SceneInterpreter` or `geometry.surface`'s own grids). For every RIGHT and DOWN adjacency between neighboring cells: if either cell has fewer than `boundary_min_support_count` valid depth pixels, the pair is `INSUFFICIENT_EVIDENCE` (both signals `None`) — this is the literal enforcement of "a missing depth measurement must not automatically become a physical boundary." Otherwise, `depth_step_m = |median(cell_A) - median(cell_B)|` (median over `depth_map`, an aggregation identical in kind to `RegionAnalyzer.depth_median_m`, not a new depth-estimation algorithm), and `orientation_change_rad = arccos(clip(normal_A . normal_B, -1, 1))` is computed OPPORTUNISTICALLY when `SurfaceEvidence` is available AND its own grid dimensions exactly equal the boundary grid's (see "Grid independence" below) — otherwise stays `None`. `state = OBSERVED_DISCONTINUITY` if `depth_step_m >= boundary_depth_step_threshold_m` **or** `orientation_change_rad >= boundary_orientation_change_threshold_rad` (either signal alone suffices — this is what lets a same-distance, differently-oriented corner register as a supported discontinuity, per the D5 task's explicit requirement), else `NO_DISCONTINUITY`.

**Discontinuity definitions:** *depth discontinuity* = a metric depth-step between two adjacent cells' median depths meeting or exceeding `boundary_depth_step_threshold_m` (default 0.15 m). *Surface-orientation discontinuity* = an angle between two adjacent cells' already-computed `SurfaceEvidence.normal` vectors meeting or exceeding `boundary_orientation_change_threshold_rad` (default ~30°). *"Observed geometry termination"* (named in the design brief) is deliberately **not** a third state: a cell whose neighbor has zero valid depth cannot be distinguished, from evidence alone, between "a real object edge where depth genuinely stops" and "a stereo-matching failure" — DPE reports the honest `INSUFFICIENT_EVIDENCE`, never a fabricated claim of stronger knowledge. This is a considered design decision, not an omission.

**Invalid-vs-boundary handling:** enforced as the FIRST, unconditional check in the algorithm — support-sufficiency is evaluated before either signal is computed, so no combination of inputs can produce `OBSERVED_DISCONTINUITY`/`NO_DISCONTINUITY` from insufficient evidence. `support_fraction_from`/`support_fraction_to` remain populated even when `INSUFFICIENT_EVIDENCE` (0.0 is informative, not "no data"). Proven directly: an all-invalid neighbor and a below-threshold-support neighbor both produce `INSUFFICIENT_EVIDENCE` with both signals `None` (`tests/test_boundary_geometry.py::TestInvalidDepthNotFabricatedIntoBoundary`, `TestInsufficientSupportRemainsUnknown`).

**Grid independence:** `boundary_grid_rows`/`boundary_grid_cols` are configured independently of `RegionEvidence`'s (`traversability_grid_rows`/`cols`) and `SurfaceEvidence`'s (`surface_grid_rows`/`cols`) own grids — neither existing type was redesigned or forced onto a shared grid, per the explicit D5 boundary rule. Orientation evidence is consulted only when the caller's `surface_grid_rows`/`cols` happen to exactly equal `boundary_grid_rows`/`cols` (both default to 3x3, so they align out of the box without DPE forcing anything); when they don't match, `orientation_change_rad` simply stays `None` for every pair, falling back to depth-only evidence — proven in `tests/test_boundary_geometry.py::TestSurfaceOrientationDiscontinuity::test_mismatched_surface_grid_falls_back_to_depth_only`.

**`GeometryFrame` addition:** `boundary_evidence: Optional[List[BoundaryEvidence]]`, appended as the new last field. Like D4's `surface_evidence` (genuinely new computation, not an extraction), `DepthPerceptionResult.boundary_evidence` is a real new field too; `build_geometry_frame()` reads it by object identity, zero recomputation (proven in `TestGeometryFrameExposesBoundaryEvidence::test_zero_recomputation_same_object_as_result`).

**Config:** `enable_boundary_geometry: bool = False` — deliberately **not** nested under `enable_geometry` (unlike `enable_surface_geometry`): its baseline signal needs only `depth_map`, a Level 0 output present regardless of any other flag, the same independence `enable_temporal` already has. `boundary_grid_rows`/`cols: int = 3` (validated `>= 1`), `boundary_min_support_count: int = 30` (validated `>= 1`), `boundary_depth_step_threshold_m: float = 0.15` (validated `> 0`), `boundary_orientation_change_threshold_rad: float = 0.5236` (~30°, validated in `(0, pi]`). All default-preserving; `mp01_perception` and every legacy field unaffected — proven byte-identical in `TestLegacyOutputsUnchanged`.

**Performance (measured, not estimated):** dev-container CPU, 320x240 synthetic stereo, 20-frame average. Depth-only (no `enable_geometry`, default 3x3 grid): 13.05 ms/frame → 13.24 ms/frame with `enable_boundary_geometry` — **+0.19 ms/frame (~1.5%)**. Full chain with orientation-enhanced boundaries (`enable_geometry`+`enable_surface_geometry`+`enable_boundary_geometry`, matching 3x3 grids): 26.98 ms/frame → 28.45 ms/frame — **+1.47 ms/frame (~5.4%)**. Bounded by grid cell/edge count, not image resolution.

**Tier 1 exports:** `BoundaryEvidence`, plus its state-constant classes `BoundaryState` and `BoundaryDirection` (needed to interpret `.state`/`.direction`, same "promote the enum alongside the dataclass" precedent as every prior phase). `geometry.boundary.build_boundary_evidence` (the algorithm) stays Tier 3.

**Tests:** `tests/test_boundary_geometry.py` (new, 23 tests) covering all 12 D5 scenarios — flat-plane no-false-positives, an analytically exact depth step (grid boundary aligned with the step, expected `depth_step_m` hand-derivable), a controlled orientation-only discontinuity (identical depth, perpendicular normals), grid-mismatch fallback, non-fabrication on invalid/insufficient data, determinism (exact dataclass equality — `BoundaryEvidence` carries no array fields, so this is a direct, not approximate, proof), spatial/frame contract, full-pipeline `GeometryFrame` exposure with object-identity zero-recomputation proof (including a variant with `enable_geometry=False` proving the depth-only baseline needs no `PointCloud`), the disabled-flag path, legacy-output byte-identity, and no-behavioral/no-opening-inference leakage. Plus 3 existing frozen-contract tests updated. Full suite: **799 passed, 0 failed**.

**Architectural issues discovered:** none new. D3's carried-forward `ClearanceEvidence` coverage-field decision remains open. The D4-flagged grid-reconciliation question (RegionEvidence/SurfaceEvidence grids) is now partially answered by precedent — D5 shows the "reconcile opportunistically, default to the same 3x3, fall back gracefully on mismatch" pattern works well and could be reused rather than forcing unification, should a future phase want RegionEvidence/ClearanceEvidence spatially correlated with SurfaceEvidence/BoundaryEvidence too.

## D6 implementation record

**Goal, restated:** identify observable gaps/openings in physical geometry — "a geometrically supported gap between surrounding physical structures," never "safe/passable/traversable for this vehicle."

**`OpeningEvidence`** (`geometry/opening.py`, new module — co-located with its algorithm, same "type + producer together" convention D4/D5 established): `frame_id` (generic, copied from the caller), `row`/`col_start`/`col_end` (the confirmed span's own grid identity — stable, self-describing, not a fragile positional index into `boundary_evidence`, per the D6 design brief's explicit warning against fragile internal references), `x1`/`y1`/`x2`/`y2` (pixel-space bounding box of the span), `approx_range_m`/`approx_width_m`/`approx_height_m` (metric estimates — see below), `support_fraction` (the weakest interior cell's own coverage), `at_image_boundary` (explicit partial/truncated-opening marker). Unlike `BoundaryEvidence`/`SurfaceEvidence` (one record per grid cell/pair, always, including an explicit no-finding state), `OpeningEvidence` is a **positive-findings-only list** — a span with insufficient support or no qualifying gap produces no record at all; an empty list is exactly how "no opening this frame" is represented. This is a deliberate contract difference, documented explicitly in `opening.py`'s own module docstring, not an inconsistency.

**Algorithm/evidence used:** built entirely from this frame's already-computed `boundary_evidence` (D5 — confirms REAL structural transitions, never reclassified) plus `depth_map` (the one signal `BoundaryEvidence.depth_step_m`'s unsigned magnitude cannot give: which side is farther) plus `focal_length_px` (already-available calibration scalar, for an explicitly-approximate pinhole width/height back-projection: `apparent_size_m = pixel_extent * range_m / focal_length_px`). Runs on the SAME `boundary_grid_rows`/`boundary_grid_cols` grid `boundary_evidence` itself used (and reuses `boundary_min_support_count` directly) — this is *consuming* boundary's own already-chosen grid, not inventing or forcing a third independent one; no `opening_grid_rows`/`cols` config exists. `geometry.FreeSpaceRays`/`geometry.ObstacleCloud` (unorganized, no per-cell grid correlation) and `geometry.surface.SurfaceEvidence` (a real, identified, not-yet-built refinement) are deliberately **not** consumed — both decisions documented explicitly in `opening.py`'s own module docstring, not silent omissions.

**Real opening vs. invalid/missing depth — the admission rule (ALL required, never any one alone):** (1) at least one flanking cell-adjacency must be a REAL, already-confirmed `BoundaryEvidence` `RIGHT`-edge with `state == OBSERVED_DISCONTINUITY` — a span with **neither** side confirmed (e.g. a smoothly receding surface, no genuine structural jump anywhere) is never admitted, regardless of how its depth varies; (2) every cell inside the span must clear `boundary_min_support_count` valid depth pixels; (3) every cell inside the span must have its own median depth at least `opening_min_range_ratio` times the FARTHER confirmed flanking structure's own median depth — this is the check that structurally prevents a near-side protrusion (an obstacle poking forward also produces a large `|depth step|`, but in the wrong direction) from ever being mistaken for an opening; (4) a span touching the image edge is admitted only if its OTHER side has a real confirmed flank, reported with `at_image_boundary=True` — an honest signal that the opening's true extent beyond the observed frame is unknown, not silently treated as either fully bounded or dropped. Proven directly: a flat/uniform depth map produces zero openings (`TestContinuousWallProducesNoFalseOpening`); a "gap" with zero valid depth, or with support below threshold, produces zero openings even though the (fabricated, absent) reading would otherwise look "far" (`TestInvalidDepthDoesNotBecomeAnOpening`, `TestInsufficientSupportRemainsUnknown`); a genuine 3-zone near/far/near scene produces exactly one confirmed opening at the correct grid cell (`TestRealOpeningProducesEvidence`); a 2-zone scene with the far zone at the image edge produces exactly one confirmed opening marked `at_image_boundary=True` (`TestPartialOpeningAtImageBoundary`).

**`GeometryFrame` addition:** `opening_evidence: Optional[List[OpeningEvidence]]`, appended as the new last field. Like D4/D5's genuinely new computed fields, `DepthPerceptionResult.opening_evidence` is a real new field too; `build_geometry_frame()` reads it by object identity, zero recomputation.

**Config:** `enable_opening_geometry: bool = False` — nested under `enable_boundary_geometry` (opening inference structurally requires `boundary_evidence`; nothing to build from otherwise). `opening_min_range_ratio: float = 1.5` (validated `> 1.0`) — the only new numeric threshold; no `opening_grid_rows`/`cols`/`min_support_count` exists, since those are always boundary's own. All default-preserving; `mp01_perception` and every legacy field unaffected — proven byte-identical in `TestLegacyOutputsUnchanged`.

**Performance (measured, not estimated):** dev-container CPU, 320x240 synthetic stereo, 60-frame average (after 3 warmup frames, to reduce first-call/JIT-adjacent noise): boundary-only 12.13 ms/frame → boundary+opening 12.62 ms/frame — **+0.49 ms/frame (~4%)**. Bounded by grid cell/edge count (identical to D5's own bound, since opening reuses boundary's grid), not image resolution.

**Public exports:** `OpeningEvidence` (Tier 1). `geometry.opening.build_opening_evidence` (the algorithm) stays Tier 3, same "promote the type, not the producer" rule.

**Tests:** `tests/test_opening_geometry.py` (new, 22 tests) covering all 14 D6 scenarios — a genuine confirmed opening from controlled 3-zone synthetic geometry (using the REAL `build_boundary_evidence` as input, not hand-faked `BoundaryEvidence`, for realism), width/height formula correctness against known pixel extents, continuous-wall no-false-positive, invalid-depth and insufficient-support non-fabrication, a partial opening at the image boundary plus its fully-bounded and zero-flank counterexamples, exact-equality determinism, frame/coordinate contract plus constructor validation, full-pipeline `GeometryFrame` exposure with object-identity zero-recomputation proof, both nesting-disabled paths (boundary off, or opening off with boundary on), legacy-output byte-identity, and no-behavioral-leakage (field-name, import-surface, and signature checks). Plus 3 existing frozen-contract tests updated. Full suite: **821 passed, 0 failed**.

**Architectural issues discovered:** none new. D3's carried-forward `ClearanceEvidence` coverage-field decision remains open. D6 confirms the "consume an existing grid rather than inventing an independent one" pattern (already used for boundary+surface opportunistic matching in D5) generalizes cleanly to a THIRD layer (opening consuming boundary's grid outright, not just opportunistically) — a reusable precedent for any future evidence type built directly on top of another, rather than beside it.

**Bearing derivation:** the standard pinhole formula, `atan2(pixel_x - principal_point_x_px, focal_length_px)`, applied to each sector's own `(x1+x2)/2`, `x1`, and `x2` pixel columns — using the pipeline's own already-computed `self._rectified_focal_length_px`/`self._rectified_principal_point_px` (the same Q-matrix-derived values rotation compensation and surface/boundary/opening geometry already use; no new camera-geometry computation). **Frame:** the optical axis of `frame_id` (always `FrameId.CAMERA_OPTICAL_LEFT` in this pipeline's actual usage). **Units:** radians. **Sign convention:** positive means the column lies toward increasing image-x (right of the principal point, and toward positive X in `CAMERA_OPTICAL_LEFT`'s own X-right/Y-down/Z-forward convention); negative means left; exactly `0.0` at the principal point's own column. **Center vs. bounds:** `bearing_center_rad` is the sector's own midpoint bearing; `bearing_min_rad`/`bearing_max_rad` are its two edge columns' bearings — always `bearing_min_rad <= bearing_center_rad <= bearing_max_rad` (the pinhole formula is strictly monotonic in pixel column for fixed, positive focal length). ## D8 implementation record

**Goal, restated:** establish coherent quality, validity, and uncertainty semantics across the whole provider contract — "what geometric evidence is trustworthy, what is degraded or unsupported, and why" — without collapsing everything into one meaningless float, and without silently redefining legacy `DepthPerceptionResult.confidence`.

**Inventory (FIRST INSPECT):** every current `GeometryFrame` field was audited for existing validity/support/coverage/confidence/quality/reliability/degraded-unknown/temporal-quality notions. Four already have a precise, single, frame-level STATE of their own: `geometry_metrics.valid_fraction` (via the pre-existing `geometry.geometry_metrics.classify_geometry_quality()`/`GeometryQuality`, Phase E6, opt-in, not previously wired into the pipeline), `temporal_consistency.state` (`TemporalConsistencyState`, Phase E3), `motion_aware_reliability.state` (`MotionAwareReliabilityState`, Phase E6 — itself already an aggregate of E3+E4+E5), `temporal_persistence.state` (`TemporalPersistenceState`, Phase E7, the frame-level gate, not the per-cell grid). Five more are per-cell/per-sector/per-span LISTS with their own self-described support (`RegionEvidence.valid_fraction`, `ClearanceEvidence.coverage_fraction`/`support_state`, `SurfaceEvidence.support_fraction`, `BoundaryEvidence.support_fraction_from/to`/`state`, `OpeningEvidence.support_fraction`) — no single existing frame-level scalar summarizes any of these. `DepthPerceptionResult.confidence` is a fifth, wholly separate, legacy per-region `RegionAnalyzer` blend, structurally unrelated to any of the above.

**Naming collision avoided, deliberately:** this codebase already has a class literally named `GeometryQuality` (`geometry/geometry_metrics.py`, Phase E6, HEALTHY/DEGRADED/NO_USABLE_GEOMETRY, single-signal). The new D8 type is named **`GeometryFrameQuality`** (not `GeometryQuality`) specifically to avoid colliding with or being confused for that narrower, pre-existing, unchanged type — `GeometryFrameQuality.geometry_validity_state` is *derived from* `GeometryQuality` via the existing classifier, not a replacement or a same-named redefinition. Flagged explicitly here since the task's own "GeometryQuality-style contract" phrasing could otherwise be misread as a name mandate.

**Exact `GeometryFrameQuality` contract** (`geometry/provider.py`, co-located with `GeometryFrame` — a pure rollup, no new algorithm, same "provider.py = types + trivial classification" precedent as `RegionEvidence`/`ClearanceEvidence`):

```python
class GeometryFrameQualityState:
    VALID = "VALID"; DEGRADED = "DEGRADED"; INSUFFICIENT = "INSUFFICIENT"

@dataclass(frozen=True, slots=True)
class GeometryFrameQuality:
    overall_state: str
    geometry_validity_state: Optional[str]
    temporal_consistency_state: Optional[str]
    motion_reliability_state: Optional[str]
    persistence_state: Optional[str]
    degradation_reasons: List[str]
```

**Quality-state definitions:** `VALID` — the dimension's underlying evidence was computed and found trustworthy. `DEGRADED` — computed, and an ACTIVE, confirmed problem was found (not merely an absence of information). `INSUFFICIENT` — computed, but there wasn't enough evidence to judge either way. A dimension is `None` when the underlying DPE capability was never enabled/computed this frame at all — see "absent vs. degraded" below.

**Derivation of every quality field:**
- `geometry_validity_state`: `classify_geometry_quality(geometry_metrics, geometry_healthy_min_valid_fraction, geometry_degraded_min_valid_fraction)` — the EXISTING classifier and the EXISTING `PipelineConfig` thresholds, no new threshold. `HEALTHY→VALID`, `DEGRADED→DEGRADED`, `NO_USABLE_GEOMETRY→INSUFFICIENT`.
- `temporal_consistency_state`: `temporal_consistency.state`. `CONSISTENT→VALID`, `CONTRADICTORY→DEGRADED`, `NOT_COMPARABLE`/`INSUFFICIENT_EVIDENCE→INSUFFICIENT`.
- `motion_reliability_state`: `motion_aware_reliability.state`. `RELIABLE→VALID`, `DEGRADED`/`UNRELIABLE→DEGRADED`, `INSUFFICIENT_EVIDENCE→INSUFFICIENT`. Deliberately stands in for Phase E4 (stabilization) and E5 (rotation compensation) too — `MotionAwareReliability` was itself already designed as "whether temporal_consistency/temporal_stabilization remain trustworthy given this frame's motion conditions," so a separate stabilization dimension would be redundant, not additional; `GeometryFrame.temporal_stabilization.state` remains directly readable regardless.
- `persistence_state`: `temporal_persistence.state` (the frame-level gate). `CLASSIFIED→VALID`, `UNRELIABLE→DEGRADED`, `INSUFFICIENT_EVIDENCE→INSUFFICIENT`.
- `overall_state`: DEGRADED if any DEFINED dimension is DEGRADED; else INSUFFICIENT if any defined dimension is INSUFFICIENT, OR if every dimension is `None`; else VALID. A fixed, documented, "an active problem always takes priority over an absence of judgment" rule — not a claim about per-dimension severity in general, applied identically regardless of which dimension triggered it.
- `degradation_reasons`: `["{DIMENSION}:{STATE}", ...]` in fixed order (`GEOMETRY_VALIDITY`, `TEMPORAL_CONSISTENCY`, `MOTION_RELIABILITY`, `PERSISTENCE`) for every defined, non-VALID dimension — pure convenience, zero new information.

Deliberately **NOT** included as dimensions: `RegionEvidence`/`ClearanceEvidence`/`SurfaceEvidence`/`BoundaryEvidence`/`OpeningEvidence`. Rolling any of these per-cell/per-sector lists up into one frame-level dimension would require DPE to invent a NEW aggregation (e.g. "fraction of boundary cells that are non-INSUFFICIENT") that is not already a precisely-defined DPE metric — exactly what decision 4's IMPORTANT note forbids. Each already self-describes its own per-item support; a consumer needing a rollup computes it directly from the list DPE already exposes.

**Absent vs. degraded — how distinguished:** `None` means the underlying capability was never enabled/computed this frame (e.g. `PipelineConfig.enable_temporal` is `False`, so `temporal_consistency` itself is `None` — no evidence exists to assess). `INSUFFICIENT` means the capability WAS enabled and DID compute a real result object, but that object's own state says there wasn't enough evidence (e.g. the first frame of a sequence — `temporal_consistency.state == INSUFFICIENT_EVIDENCE`, a real, computed outcome). `DEGRADED` means the capability ran and actively found a problem (e.g. `CONTRADICTORY`). Proven as three genuinely distinct, never-conflated values (`tests/test_geometry_frame_quality.py::TestAbsentVsBadEvidence`).

**RegionEvidence change:** gained `frame_id: str` (first field, matching `SurfaceEvidence`/`BoundaryEvidence`/`OpeningEvidence`/`ClearanceEvidence`'s own per-object convention) — the one other D3-era evidence type D7 didn't touch (D7 was scoped to `ClearanceEvidence` only). `build_region_evidence()` gained a matching `frame_id: str` parameter; no other field or behavior changed.

**Compatibility:** `DepthPerceptionResult.confidence`'s own derivation (`aggregate_confidence()`, mean per-region `RegionAnalyzer` blend) is untouched — proven byte-identical regardless of `enable_geometry_frame` (`tests/test_geometry_frame_quality.py::TestLegacyConfidenceUnchanged`). **FINDING 1 (the significant one) — real StereoSGBM's smoothness prior produces implausibly confident `SurfaceEvidence` from pure noise.** Total left/right decorrelation (independent i.i.d. random-noise images, zero true correspondence) was fed through the real, unmodified pipeline across 5 independent seeds. `GeometryMetrics.valid_fraction`/`GeometryQuality` DID respond correctly (DEGRADED, measurably lower than a real scene) — but `SurfaceEvidence.planarity`, DPE's own per-cell "how well does this look like a real, well-fit plane" signal, measured **~0.99 (mean 0.9935-0.9961 across all 5 seeds)** on cells built entirely from this decorrelated noise — i.e. DPE confidently reported near-perfect planar surfaces where no real geometry existed. Root cause, confirmed by direct behavior (not merely inferred): real `StereoSGBM`'s own semi-global smoothness regularization (P1/P2 path costs) does not degrade into per-pixel-random output under total data-cost uninformativeness — it produces a spatially SMOOTH, plausible-looking disparity field (a real, general property of SGBM under total correspondence loss, not a DPE-introduced defect). `SurfaceEvidence`'s PCA fit, given no way to distinguish "a real smooth surface" from "SGBM's own smoothness-prior-driven degenerate output," honestly reports a high-quality fit to whatever points it receives — the geometric-fit computation itself is correct, but the resulting confidence signal materially overstates trustworthiness of the underlying evidence. Compounding: `depth_perception_engine.quality.looks_like_garbage_frame()` — a garbage/uncorrelated-frame detector that already exists in this codebase precisely for this class of input — is never invoked anywhere inside `pipeline.py`'s own `process()` path (confirmed by source grep, zero call sites), and `GeometryFrameQuality` (D8) does not include `SurfaceEvidence` as one of its four rollup dimensions (a deliberate D8 design choice, documented at the time, not reconsidered here). **Classified: VALIDATION FAILURE — a real false-positive risk ("noise != supported surface"), not fabricated depth/obstacle/free-space geometry (which stayed correctly gated by `valid_mask` throughout) but a confidence-signal over-claim on the ONE evidence family (`SurfaceEvidence`) whose entire purpose is expressing fit confidence.** Not fixed here, per this phase's explicit "no automatic repair" instruction — flagged as a candidate for a future, separately-scoped corrective phase (e.g. wiring `looks_like_garbage_frame()` upstream of geometry computation, or a texture/entropy-aware planarity discount). The new test asserting this finding (`TestSevereDecorrelatedNoiseFalsePositiveSafety::test_total_decorrelation_yields_high_confidence_surface_evidence_from_noise`) is deliberately written to FAIL if a future fix lowers this planarity — documented in the test's own docstring as "if this now fails, the false-positive was fixed upstream, not a new regression."

**FINDING 2 (minor) — `RotationCompensationStatus.APPLIED` is reported even when the underlying compensation was fully NaN-poisoned and produced zero usable output.** A `MotionHint` with NaN (or Inf) inside `angular_velocity_rad_s` — a value `MotionHint.__post_init__` does not validate — passes `select_motion_hint_samples()`'s own finite-TIMESTAMP-only filter untouched, poisons `integrate_angular_velocity()`'s integrated rotation with NaN, which poisons `_reproject_source_to_target()`'s intermediate `u_r`/`v_r` (producing a `RuntimeWarning: invalid value encountered in cast` when NaN is cast to `int64`). Traced precisely: the resulting garbage index fails the existing `in_bounds` check (a NaN→int64 cast reliably lands far outside `[0, h_dec)`/`[0, w_dec)` on this platform), so `scatter_mask` ends up entirely `False` and the compensated snapshot is correctly all-zero (this codebase's own "0.0 is invalid, never fabricated" convention) — **no unsafe geometry was fabricated; the actual safety property held**, and `temporal_consistency` correctly falls back to `INSUFFICIENT_EVIDENCE` downstream, exactly as it should given zero usable compensated data. The one real inconsistency: `rotation_compensation_status` still reads `APPLIED` ("a relative rotation was successfully integrated... and used to re-project the previous frame's geometry," per that constant's own docstring) even though the actual reprojection produced nothing usable at all. **Classified: VALIDATION FINDING (status-label inconsistency, not a fabrication/safety violation).** Not fixed here.

### B. Surface-normal regression audit — root cause found, verdict: no code defect, algorithm left unchanged

**Restated finding (from the external MP01-sim integration, not re-derived here):** `obstacle_box_3`'s `SurfaceEvidence` angular error, measured on an identical Gazebo scene/grid/calibration/config, changed from 20.3 deg (planarity 0.927, DPE v1.0.1) to 48.1 deg (planarity 0.808, DPE v1.1.0/v1.1.1).

**Hypothesis 1 — the I1-I6.3 shadow-zone reliability mask added to `build_surface_evidence()` (the only commit touching `geometry/surface.py` between v1.0.1 and v1.1.0, `c2b1906`) excludes contaminated points from the plane fit, changing which points feed the PCA.** Tested directly: re-ran the identical live Gazebo frame's `obstacle_box_3` cell through `DepthPerceptionPipeline` with `PipelineConfig.geometry_shadow_zone_enabled=True` vs `False`. **Byte-identical result both ways** (same normal, same planarity, same support_fraction, same angular error) — the shadow-zone mask does not flag any pixel in this cell at all for this scene. **Hypothesis 1 ruled out.**

**Hypothesis 2 — the same commit's SGBM `P1`/`P2` channel-count fix (`8*3*block_size**2` -> `8*1*block_size**2`, correcting a multi-channel constant applied to grayscale-only input) and `uniquenessRatio` change (10 -> 20) alter disparity/depth values feeding this cell's point cloud, independent of any surface-specific logic.** This fix is itself real, deliberate, and already independently measured (offline: 41.8% -> 0.27% false-valid-disparity on decorrelated input) — not new tuning, already applied and validated at v1.1.0. Not reverted or touched here (out of scope, and reverting a proven fix to make one external fixture's number look better is exactly the "tune against Gazebo" behavior this phase is explicitly not permitted to do).

**Generalization check — is a ~48 deg error on a moderate-planarity, partial-coverage cell a NEW characteristic, or an already-known one?** Re-ran `benchmarks/i5_surface_opening_clearance/surface/measure.py` (offline, analytic ground truth, no Gazebo, unchanged fixture set) fresh against current `v1.1.1` source: partial-coverage cells (`support_fraction` ~0.2-0.75 — an object occupying only part of a grid cell, or straddling an edge) measured a mean angular error of ~37 deg (individual cells 38-73 deg) at planarity 0.81-0.89, while full-coverage cells averaged under ~1.5 deg (one full-coverage cell reached 81.5 deg under an unfavorable texture/pose combination — the envelope is wide in general, not narrow to one fixture). `obstacle_box_3`'s own measured `support_fraction=0.731`, `planarity=0.808`, `angular_error=48.06` deg lands squarely inside this already-documented envelope, on a completely unrelated fixture set that was not touched or added to for this check.

**Verdict: no genuine structural/math/software defect found.** The regression traces to (a) an already-justified, already-applied, independently-validated disparity-engine fix changing which depth values are available to a small, coarse-grid-relative, partially-framed object's plane fit, landing it in (b) an already-known, already-characterized limitation of the current unweighted-covariance PCA fitting approach on partial-coverage cells — not a new defect introduced this release, and not specific to Gazebo. No source change was made. Per this phase's own explicit instruction, this is documented (here, and in `docs/RELEASE_NOTES_V1.md`'s "Known caveats") rather than "fixed" by tuning against the triggering fixture; a genuine fix (e.g. a robust/weighted fitting method less sensitive to partial coverage) would be real algorithm development, out of scope for a structural closure phase, and requires real-camera evidence to justify and validate against — not a synthetic Gazebo scene.
